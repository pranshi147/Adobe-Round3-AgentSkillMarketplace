[P0] F-001 · Structured data disagrees with the visible page  (high, TRUST, confidence 0.88)
  Why it matters: A research agent can quote a price, name or availability that the page
  does not actually show.
  Mechanism: Structured data is trusted precisely because it is unambiguous. When JSON-
  LD asserts a price, name or availability that appears nowhere in the visible text, a
  system reading the markup extracts a fact the page itself does not support — producing
  a confidently-stated wrong answer rather than a missing one.
  Evidence:
    - http://demo.example.com/product-blender.html — JSON-LD price does not match the
    visible page [structured value="999"; visible value(s)="1299"]
  Fix: Make price in JSON-LD render from the same source as the visible value on
  http://demo.example.com/product-blender.html.
    - Bind the JSON-LD field to the same data source that renders the visible value,
    rather than a separate constant or feed.
    - Add a build/CI assertion that fails when the serialised markup value differs from
    the rendered value.
    - Where the markup is intentionally a starting price, use the correct schema field
    (e.g. lowPrice within AggregateOffer) and reflect that in the visible copy.
  Verify: Fetch the page, extract the JSON-LD field and the visible value, and confirm
  they match; re-run the audit.
  Effort: medium

[P0] F-002 · Canonical URLs conflict with page identity  (high, IDENTIFY, confidence 0.9)
  Why it matters: Content is attributed to the wrong URL, or dropped as a duplicate,
  making a stable citation target impossible.
  Mechanism: rel=canonical tells a retrieval system which URL *is* this document. When
  it points off-site, to a dead URL, or collapses pages with materially different
  content onto one address, the machine either attributes the content to the wrong
  address or discards the page as a duplicate — so a citation cannot resolve back to it.
  Evidence:
    - http://demo.example.com/ — two pages with materially different content declare the
    same canonical URL [other page=http://demo.example.com/city-picker.html; shared
    canonical=http://demo.example.com/; main-text similarity=0.00]
    - http://demo.example.com/city-picker.html — two pages with materially different
    content declare the same canonical URL [other
    page=http://demo.example.com/mismatch.html; shared
    canonical=http://demo.example.com/; main-text similarity=0.00]
  Fix: Point each page's rel=canonical at its own live, preferred URL.
    - Set rel=canonical to the page's own absolute HTTPS URL unless it is a genuine
    duplicate.
    - Where pages truly duplicate one another, keep the canonical but make the
    duplicate's content identical, or differentiate the content and give each its own
    canonical.
    - Remove canonicals pointing at URLs that do not return 200.
  Verify: Fetch each affected page, confirm the canonical resolves to a 200 URL that
  serves the same content, and re-run the audit.
  Effort: small

[P1] F-003 · The site names its own brand inconsistently  (high, IDENTIFY, confidence 0.85)
  Why it matters: Claims from this site may be attributed to the wrong organisation, or
  not connected to the brand at all.
  Mechanism: An entity-resolution step answers 'which organisation is this?' by
  reconciling the title suffix, og:site_name, Organization/WebSite JSON-LD, the logo alt
  text and the copyright line. When these disagree in ways that are not simple
  abbreviations, the entity cannot be pinned to one name, and claims found here may be
  attributed to a different organisation or merged with a similarly-named one.
  Evidence:
    - http://demo.example.com/ — brand name asserted by og:site_name [value="Zenith
    Retail" (normalised: "zenith retail")]
    - http://demo.example.com/ — brand name asserted by Organization/WebSite JSON-LD
    name [value="Apex Commerce Pvt Ltd" (normalised: "apex commerce")]
    - http://demo.example.com/ — brand name asserted by logo alt text [value="Zenith
    Retail" (normalised: "zenith retail")]
  Fix: Publish one canonical brand name and use it identically in every identity
  surface.
    - Choose the canonical legal/trading name and apply it to og:site_name, the
    Organization JSON-LD `name`, the logo alt text and the copyright line.
    - Add `alternateName` to the Organization JSON-LD for legitimate variants rather
    than using them interchangeably.
    - Add `sameAs` identifiers (official social, Wikipedia/Wikidata, registry listings)
    so the entity resolves to one node.
  Verify: Re-run the audit and confirm all name sources normalise to the same value;
  check the Organization JSON-LD parses and contains sameAs.
  Effort: small

LIMITATIONS OF THIS AUDIT
----------------------------------------------------------------------------------------
  - Partial audit: fewer pages were read than requested, so shares and breadth are
  measured over a small sample. Findings remain valid for the pages named.
  - The audit reads served HTML only and does not execute JavaScript. Pages whose
  content is assembled client-side are reported as what a non-rendering fetcher
  observes; the rendered state was not performed — no browser engine was used; all pages
  judged from served HTML.
  - Off-site corroboration is limited to the external identifiers the site itself
  declares. No search engine or directory was consulted, no claim is made about whether
  any AI product uses this site, and the absence of external references is never treated
  as a defect.
  - 13 page(s) were sampled under a 20-page / 60s budget; findings describe the sample,
  and shares are reported relative to it.
  - 1 URL(s) were not fetched because robots.txt disallows them; they are reported as
  findings, not inspected.
